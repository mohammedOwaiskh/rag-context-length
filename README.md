# Impact of Context Length on RAG

**How Much Context Is Enough? Investigating the Impact of Retrieval Context Length on RAG-Based Question Answering**

A controlled RAG experiment measuring how the number of retrieved passages (`k`) fed to a generator affects downstream QA performance, with retrieval success and generation success analyzed separately.

## Research question

Does increasing the number of retrieved passages consistently improve answer quality, or is there an optimal retrieval context size beyond which additional context becomes ineffective or harmful?

## Key findings

On 1,500 SQuAD v1.1 questions with Qwen2.5-3B-Instruct (4-bit):

- **Recall keeps rising with `k`, answer quality does not.** Recall@k climbs from 0.59 (k=1) to 0.91 (k=20), but F1 peaks at k=10 (0.564) and drops at k=20 (0.539).
- **Most of the gain comes early.** F1 rises from 0.455 (k=1) to 0.548 (k=3); k=5 and k=10 add only small further gains.
- **Conditional on the gold passage being retrieved, F1 falls monotonically with `k`** (0.717 at k=1 → 0.581 at k=20). With the right evidence present, extra context makes the generator less accurate.
- Results are specific to this setup (one dataset, retriever, and generator; see [Limitations](#limitations)).

## Pipeline

```
Question → MiniLM embedding → FAISS top-20 retrieval → top-k context slice → Qwen2.5-3B-Instruct → generated answer → EM / F1
```

## Method

| Component | Choice |
|---|---|
| Dataset | SQuAD v1.1 (`train` split), 1,500 questions, seed=42 |
| Corpus | Full deduplicated set of SQuAD contexts (~18–20K passages), not just gold passages |
| Embedding model | `sentence-transformers/all-MiniLM-L6-v2` |
| Index | FAISS `IndexFlatIP` (cosine via normalized inner product) |
| Generator | `Qwen/Qwen2.5-3B-Instruct` (4-bit via bitsandbytes on GPU; Q4_K_M GGUF as CPU-only option) |
| k values | 1, 3, 5, 10, 20 (retrieved once as top-20, sliced as nested prefixes) |
| Generation | Deterministic: `do_sample=False`, `temperature=0`, `max_new_tokens=20`, batch size 8 |
| Prompt | Fixed across all k; instructs the model to answer with a short extractive span from the context |
| Metrics | Token-level F1 (primary), Exact Match (secondary), Recall@k, average context tokens, F1/EM conditional on gold-passage retrieval |
| Uncertainty | 95% percentile bootstrap CIs (2,000 resamples, seed=42) on F1 |

Full configuration is frozen in [`config.yaml`](./config.yaml) — every script reads from it rather than hardcoding constants.

## Setup

```bash
git clone https://github.com/mohammedOwaiskh/rag-context-length.git
cd rag-context-length
pip install -e .
```

The editable install puts `retrieval`, `generation`, `evaluation`, and `experiments` on the path as top-level packages (src-layout), so the modules can be run from anywhere in the repo with `python -m`.

## Running the pipeline

Run from the repo root, so each script finds `config.yaml`.

```bash
# Phase 1 — retrieval baseline
python -m retrieval.build_corpus
python -m retrieval.sample_questions
python -m retrieval.embed_corpus
python -m retrieval.retrieve          # prints Recall@k

# Phase 2 — pilot (75 questions, all k)
python -m experiments.run_pilot

# Phase 3 — main experiment (1,500 questions × 5 k-values)
python -m experiments.run_main_experiment

# Phase 4 — figures for the poster
python -m evaluation.make_plots
```
The main experiment is **resume-safe**: results are appended per question and already-completed (question, k) pairs are skipped on restart. This lets the full run be split across several Colab free-tier sessions (~3 hours each). Generation is batched (`batch_size: 8`, left-padded); lower it in `config.yaml` if k=10/20 runs out of memory on a T4.

On Colab, use `notebooks/colab_runner.ipynb`, which calls the same scripts.

## Experimental design

Retriever, embedding model, generator, prompt template, generation settings, and question set are held fixed across all k-conditions, isolating retrieval depth as the independent variable. Top-20 is retrieved once per question and the smaller conditions are nested prefixes of that list, so retrieval randomness cannot explain differences between k values.

**Pilot findings that shaped the final settings.** The 75-question pilot showed EM ≈ 0 at every k because the model produced verbose, non-span answers. The prompt was tightened to demand short spans and `max_new_tokens` was lowered to 20. The pilot also projected a ~13-hour full run, which motivated batched, resume-safe generation.

## Key analyses

- **Main table:** Recall@k, EM, F1, and average context token count at each k.
- **Conditional F1:** answer F1 restricted to questions where the gold passage was retrieved — separates generation/context-utilization failures from retrieval failures.
- **Bootstrap CIs:** 95% intervals on overall and conditional F1.

## Reproducibility

- Fixed seed (`42`) for question sampling and bootstrap resampling.
- Deterministic generation (`do_sample=False`, `temperature=0`).
- Retrieval computed once at top-20 and sliced, not re-queried per k.
- Per-question raw outputs saved as JSONL (`results/main/results_k{k}.jsonl`) after generation.
- Main experiment run on a Colab T4 (4-bit, `hf_bnb` backend). Library versions and hardware are recorded in the `reproducibility` section of `config.yaml`.

## Limitations

Single QA dataset (SQuAD v1.1, primarily extractive), single embedding model, single retriever, single generator. Passage count is only an approximation of true context length (token counts are recorded separately), and `k` conflates "more evidence" with "more noise" — a dedicated distractor experiment that adds irrelevant passages to a fixed relevant one was planned but is not part of this study, so the dilution explanation is supported by the conditional-F1 trend rather than tested directly. Evidence position ("lost in the middle") was not analyzed. The generator may have seen SQuAD during pretraining, so results are read as relative comparisons across context conditions rather than claims about unseen-world QA accuracy.
